Texture File Scheme for Permutation Models
============================================

Background
----------
Permutation models (e.g. farmhouses) have multiple "skins" sharing the same
geometry. The mode tag's model_permutation_data table maps each permutation x
material pair to a view index -- which frame in the .256 collection's sequence
to display.

PNG naming convention: <collection_tag>_<sequence>_<view>.png
  e.g. fate_2_5.png = collection "fate", sequence 2 (left), view 5

Root Cause
----------
Two independent bugs caused permutation models to always emit textures from
view index 0 instead of the correct variant:

Bug 1 -- Wrong offset for permutations_offset (myth2_model.cpp:1171)
  The code read byte [24:28] (a zeroed runtime pointer `vertex_flags`)
  instead of byte [28:32] (the persistent `model_permutations_offset`).
  Since byte 24 was always 0, permBase resolved to 64+0=64 (reading vertex
  flag data as permutation data) instead of 64+376=440 (the real table).

  From model_definitions.h (reference source):
    [24:28]  vertex_flags              (runtime pointer, zeroed on disk)
    [28:32]  model_permutations_offset (persistent on-disk field)

  Fix: readBE32s(modeData.data(), 24) -> readBE32s(modeData.data(), 28)

Bug 2 -- View index clamped instead of modulo
  The old code clamped: if (vi >= numViews) vi = 0. Since most permutation
  view indices (9, 13, 16, 22) exceeded the stored sequence frame counts
  (2-10), this always gave view 0 for every material.

  The stored number_of_views field at seqDataAbs+8 is correct. The fix is
  modulo arithmetic within the same sequence:

  Fix: vi %= nv

  An earlier attempt used an even-odd pair spanning algorithm, which appeared
  correct because the paired sequences (front/back, left/right) have identical
  pixel dimensions and only differ by subtle shading (simulating shadow on
  opposite sides of symmetrical buildings). The textures were too similar to
  notice the mismatch.

  Another attempt scanned the bitmap_instance_indexes array past the stored
  count, but this read into adjacent data and produced wrong textures.

View Resolution Algorithm (myth2_model.cpp, modulo within sequence)
-------------------------------------------------------------------
  // Step 1: Get frame count from stored sequence header field
  int nv = dot256SequenceViewCount(collData, mat.sequenceIndex);

  // Step 2: Resolve view index within this count (same sequence only)
  int vi = (int)(*matViews)[mi];
  if (nv > 0) vi %= nv;
  else vi = 0;

  // Result: vi = view within the starting sequence
  // PNG = <collection>_<seq>_<vi>.png

Files Modified
--------------
  myth2_model.cpp:1171 -- readBE32s offset 24 -> 28
  myth2_model.cpp -- view resolution changed from clamp to modulo

Context: Tag Install Strategy
-----------------------------
  Three tag installs must all be loaded for full extraction:
    small_install.dng2  -- mode tags (model definitions, permutations)
    medium_install.dng2 -- geom tags (geometry, materials, vertices)
    large_install.dng2  -- .256 collections (bitmap sequences, textures)

  The .256 collections exist ONLY in the large install; trying to filter
  findTagInFile by source file breaks texture lookup. All three installs
  must be loaded simultaneously.

Validated
---------
  Tested against le3e farmhouse instances with fate collection. Sequence
  frame counts: seq 0=10, seq 1=10, seq 2=8, seq 3=8, seq 4=2.

  For perm 2 views {16, 5, 7, 22, 0}:
    left  (seq 2) view 16 % 8      -> fate_2_0
    right (seq 3) view 5           -> fate_3_5
    front (seq 0) view 7           -> fate_0_7
    back  (seq 1) view 22 % 10     -> fate_1_2
    roof  (seq 4) view 0           -> fate_4_0

  The permutation view indices wrap via modulo within each sequence.
  No sequence pairing or spanning is involved.

Why Raw View Selectors Can Exceed number_of_views
-------------------------------------------------
  The mode permutation byte should be treated as a raw view selector, not as
  an already-normalized index into the material sequence's bitmap list. Oak
  exposes the same condition in its editor, for example "view 17 of 8" or
  "view 23 of 10"; Oak's display is 1-based, so these correspond to stored
  selector values 16 and 22.

  This is expected:

    stored 16 on an 8-view sequence  -> 16 % 8  -> view 0
    stored 22 on a 10-view sequence -> 22 % 10 -> view 2

  The best current interpretation is that the selector records the authored
  variation phase for a material, and the .256 sequence lookup resolves that
  selector against the sequence's own number_of_views. Different building
  sides can therefore share one permutation row while each side has a different
  frame count: fate_0 and fate_1 have 10 views, fate_2 and fate_3 have 8, and
  fate_4 has 2.

  Keeping the raw selector is useful to the authoring pipeline because it does
  not destroy information. If a sequence later gains more frames, selector 16
  is no longer equivalent to normalized view 0. The shipped tags and Oak both
  preserve the raw value, while the runtime result matches modulo resolution.

Appendix: model_permutation_delta (scen tag, bytes [52:54])
----------------------------------------------------------
  The scen tag's scenery_definition struct has a model_permutation_delta
  field at [52:54]. When the _scenery_adjusts_model_permutation_flag is set,
  this value offsets the model permutation selection, allowing different
  instances of the same skelmodel tag to display different variations.
  Not relevant to 2D sprite-based scenery extraction.
